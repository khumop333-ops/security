1. Visual language

The interface must read as a serious, established security firm — closer to a banking or medical-alert application than a consumer app. The following rules are binding for all screens:

  • One sans-serif typeface (Inter). Hierarchy is created with weight (regular / medium / semibold / bold), not colour.
  • No gradients, no neon, no glassmorphism, no decorative animation, no illustrations, no emoji.
  • Elevation limited to a subtle 1–2 px shadow. Solid fills only.
  • Matte red is reserved exclusively for the panic button and its hold-progress ring — never for warnings, badges or links.
  • Icons are outline style with a single consistent stroke width (1.75 px at 24 px).
  • Minimum tap target 48×48 px; body text minimum 16 px; all text meets WCAG AA contrast.
  • Copy is direct, calm and instructional (“Press and hold to alert security”). No playful microcopy.

Accidental-trigger protection: the alert fires only after a deliberate continuous 3-second hold. Releasing early — or dragging off the button — aborts with no side effects. A false alarm can be cancelled from the status screen, but only with the user's PIN.

5. Accessibility & compliance notes

  • All text/background pairs meet WCAG AA (≥4.5:1 body, ≥3:1 large text). Status is never conveyed by colour alone — icons and labels accompany every badge.
  • The panic action is reachable by keyboard (Enter/Space activation) and screen readers (explicit aria-label with hold instruction).
  • Reduced-motion preference disables the hold-progress transition; the countdown text still communicates remaining time.
  • POPIA: consent is captured explicitly with a timestamp; location is only captured on alert/test; medical data is visible only to responders and the control room; access/correction/deletion requests are first-class UI actions backed by an auditable log.
  • False-alarm cancellation is PIN-protected to prevent misuse (spec requirement), and every status change is written to an immutable event log.
